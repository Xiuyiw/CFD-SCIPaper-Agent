# V0.3 Evidence-to-Figure-and-Paragraph Design

**Status:** AUTHOR APPROVED — READY FOR IMPLEMENTATION

**Date:** 2026-09-01

**Baseline:** `e01675b47f62b684d8337db2e10d902181ce0b01`

**Target release:** `v0.3.0`

## 1. Purpose

V0.3 implements one complete, testable vertical slice for researchers who already have mature CFD
results:

> canonical exported observations + existing project records → scientific qualification → locked QoI
> and discrete trend → bounded claim → one publication figure → one evidence-bound results paragraph.

The release does not attempt to generate a full manuscript. Its success is measured by whether one
ordinary researcher can take a documented steady single-phase internal-flow comparison through the
chain without a hard error in case identity, unit, QoI meaning, sequence membership, trend, figure
value, or paragraph claim.

The system remains author-in-the-loop. It does not infer missing CFD operators, invent a QoI formula,
promote incomplete evidence, or represent a generated artifact as author approval.

## 2. Product principles

Implementation follows the approved 55/25/10/10 allocation:

- 55% scientific qualification and analysis;
- 25% figure production and evidence-bound writing;
- 10% CSV intake and guided usability;
- 10% necessary persistence, provenance, and author checkpoints.

`STOP THAT SHIT` is binding. A new object, dependency, report, or workflow step is allowed only when
the current vertical slice would otherwise produce a scientifically wrong or unusable result.

The following rules are invariants:

1. Scientific qualification precedes analysis, plotting, and writing.
2. Missing information remains missing and is returned as a minimum correction request.
3. Candidate objects are not locked objects.
4. Author identity cannot repair scientific insufficiency.
5. Plotting and writing consume locked facts and cannot revise them.
6. Input changes make dependent products stale before they can be reused.
7. The authoritative execution path is the local Python CLI and deterministic code. Skills are thin
   wrappers around that path.

## 3. Scope

### 3.1 Included

V0.3 includes exactly seven work packages:

1. canonical CSV observation intake, minimal units, guided correction messages;
2. comparison qualification, separate verification/validation status, candidate QoI contract;
3. author locking of the QoI contract, QoI calculation, complete-sequence trend analysis;
4. four-level claim ceiling and candidate figure/paragraph responsibilities;
5. locked FigureContract, source-data CSV, runnable Matplotlib, SVG, PNG, and three QA dimensions;
6. one restricted results paragraph with numeric backlinks;
7. CLI integration, stale propagation, four thin Skills, public positive/negative/adversarial fixture,
   Quickstart, packaging, and compatibility tests.

### 3.2 Explicitly deferred

V0.3 does not implement:

- VTK or CGNS field analysis;
- native Fluent or STAR-CCM+ extraction;
- inferred area, volume, mass-flow, or control-volume operators;
- Pint or another full unit framework;
- PDF or TIFF figure output;
- multi-figure workspaces or a full paper;
- literature search, evidence workspace, or citation insertion;
- DOCX, LaTeX, or journal-template export;
- pre-submission review or real-review revision workflows;
- RAG, embeddings, Agent runtime, provider transport, or multi-host adapters;
- marketplace, global Skill registry, telemetry, or additional approval layers.

Existing modules that mention these future capabilities remain unchanged unless a V0.3 test must
remove a false availability claim from CLI help or documentation.

## 5. Internal package boundary

The new scientific implementation lives in `src/cfdpaper/qualification/`. It is an internal package,
not a second public contracts module.

```text
src/cfdpaper/qualification/
├── __init__.py
├── models.py          # immutable V0.3 records and closed enums
├── observations.py    # canonical CSV parser and sequence validation
├── comparison.py      # difference roles, threshold basis, V&V status, eligibility
├── qoi.py             # candidate/locked QoI and discrete analysis
├── claims.py          # four-level ceiling and candidate figure/paragraph duties
├── artifacts.py       # deterministic paths, JSON/CSV writes, fingerprints, stale checks
└── service.py         # thin qualification/analyze orchestration
```

Figure rendering and paragraph rendering remain publication responsibilities:

```text
src/cfdpaper/publication/
├── render_figure.py
└── results_paragraph.py
```

This split prevents one large orchestration module from owning CSV parsing, scientific decisions,
Matplotlib, prose, and persistence simultaneously.

## 6. Canonical observation input

### 6.1 Required CSV columns

The observation CSV uses UTF-8 and a header with exactly these required columns:

| Column | Meaning |
|---|---|
| `case_id` | Stable case identifier matching existing project records. |
| `coordinate_name` | Name of the ordered study coordinate, for example `mean_velocity`. |
| `coordinate_value` | Finite numeric coordinate value. |
| `coordinate_unit` | Known unit for the coordinate. Use `1` for dimensionless. |
| `variable` | Scientific variable name, for example `pressure_drop`. |
| `value` | Finite exported observation. |
| `value_role` | One of `raw-sample`, `declared-aggregate`, `precomputed-qoi`. |
| `unit` | Known unit for `value`. |
| `scope` | Physical scope/location, for example `inlet-to-outlet pressure difference`. |
| `source_locator` | Nonblank reproducible locator to the source export or report. |

Optional columns are:

- `aggregation`: required when `value_role=declared-aggregate`; it names the already performed
  operation, for example `area-weighted-average`. V0.3 records the declaration but does not reproduce
  an unavailable field operator.
- `statistical_window`: required when the value depends on a temporal/statistical window.
- `note`: short factual context that is not used to infer an operator.

Unknown columns are rejected. This is deliberate: accepting an unbound numeric column would make the
row appear more meaningful than the input contract allows.

### 6.2 Row rules

Each row must satisfy all of the following:

- strings are nonblank after trimming;
- numeric values are finite;
- units are known to the explicit V0.3 unit table;
- `source_locator` identifies the source, row/report location, or export object;
- `declared-aggregate` has a nonblank `aggregation`;
- `raw-sample` cannot be consumed by an aggregate QoI unless the contract defines a deterministic
  scalar operation available from those rows;
- `precomputed-qoi` can only satisfy an identity QoI whose variable, unit, scope, and locator match;
- duplicate `(case_id, coordinate_name, coordinate_value, variable, scope)` rows are rejected;
- no row is interpolated, smoothed, filled, or silently averaged.

### 6.3 Expected membership

The candidate QoI contract records an ordered list of expected members. Each member binds:

- `case_id`;
- coordinate name, value, and unit;
- expected variable and scope.

Observed membership must equal expected membership after compatible unit conversion. Missing,
unexpected, duplicated, or reordered scientific members block locking or analysis. File row order can
differ; scientific order is defined by the locked expected sequence.

### 6.4 Guided intake

Non-interactive `qualify` requires `--records project-records.json` for a new V0.3 project. This strict
intake envelope contains `cases`, `boundaries`, `models`, `convergence`, `conservation`, and
`sources`. It is validated before any write, then persisted through the existing `ProjectStore`
records (`CaseRecord`, `BoundaryRecord`, scientific assessments, and located `EvidenceRecord`s).
`ProjectStore` exposes one minimal batch-import transaction that reuses the existing record
validators and SQL write helpers: all envelope members commit together, and any validation or write
failure rolls the transaction back to zero imported members. It adds no table or public schema.
It does not create a parallel registry. Reuse without `--records` is allowed only when the store
already contains a complete, fingerprint-equivalent record set. The public fixture exercises this
route end to end through the installed CLI.

For researchers who do not already have that JSON, the equivalent interactive route is:

```text
cfdpaper qualify PROJECT_ROOT --observations observations.csv --guided
```

The scientific wizard asks, in sequence, for case identity and coordinate; boundary and model
differences plus their four comparison roles; convergence observation, threshold, consequence,
basis, and locator; conservation observation with the same threshold fields; separate verification
and validation status, basis, and locator; and source identity/locator. It displays a factual summary,
writes `project-records.json`, imports it through the same strict loader, and then performs normal
qualification. Cancellation or an incomplete required answer writes neither records nor candidate
artifacts. Users need not know the envelope's top-level schema. `--guided` and `--records` are
mutually exclusive; automation and the non-interactive Quickstart continue to use `--records`.

User-facing errors use scientific language rather than schema language. Examples:

- `Case P3 is missing from the declared velocity sequence.`
- `Pressure drop for case P2 has no source locator.`
- `The comparison changes both diameter and roughness; classify each difference before analysis.`
- `A convergence threshold was supplied without a project basis or locator.`

The report also contains stable machine-readable issue codes. The CLI prints the shortest useful
summary and the path to the complete JSON artifact.

## 7. Comparison qualification

### 7.1 Difference roles

Every case difference relevant to the comparison has exactly one role:

1. `intended-study-factor`: the factor the approved question asks to vary;
2. `demonstrated-equivalent-or-immaterial`: a difference supported by evidence as equivalent or
   immaterial for this comparison;
3. `unresolved-nuisance`: a difference that may affect the result but lacks sufficient resolution;
4. `blocking`: a difference that makes the requested comparison scientifically invalid.

The second role requires a nonblank basis and locator. Author preference alone cannot assign it.
Unresolved nuisances limit or block claim classes according to their relationship to the QoI.
Blocking differences produce `insufficient`.

### 7.2 Threshold basis

Convergence and conservation thresholds are optional only when the project explicitly records that
the assessment is unavailable. If supplied, each threshold requires:

- metric name;
- finite threshold value and unit where applicable;
- comparison operator;
- scientific/project basis;
- locator.

No library default is silently substituted. An absent threshold is represented as missing evidence,
not as a passing result.

### 7.3 Qualification status

The qualification status is one of:

- `eligible`: comparison and required numerical evidence support the declared analysis;
- `restricted`: the comparison is usable only under an explicit lower claim ceiling;
- `insufficient`: analysis, figure rendering, and paragraph rendering are blocked.

The report lists blockers, restrictions, and minimum correction requests separately.

### 7.4 Verification and validation

Numerical verification and validation are recorded independently.

`VerificationStatus` records whether the available evidence addresses the numerical solution and
implementation, including iterative convergence, conservation/solution consistency, and available
spatial or temporal refinement evidence.

`ValidationStatus` records whether the model has a relevant external comparison for its intended use.

Each status is one of `demonstrated`, `partial`, `not-demonstrated`, or `not-applicable`. `not-applicable` requires
a logical basis and locator; it cannot replace missing evidence. Validation absence can restrict a
claim without making every numerical comparison unusable.

Convergence and conservation are evaluated from located `ConvergenceObservation` and
`ConservationObservation` records, not status text. Each binds the observed metric/value/unit to a
`ThresholdBasis` containing operator, threshold, `consequence` (`blocking` or `restricting`), basis,
and locator. Exceeding a blocking threshold yields `insufficient`; exceeding a restricting threshold
yields `restricted`. A required threshold without basis or locator can never yield `eligible`.

## 8. Candidate and locked QoI contracts

### 8.1 Candidate contract

`CandidateQoIContract` is proposed by `qualify`; it is not executable until checkpoint 1.

It contains:

- stable `qoi_contract_id`;
- approved topic and research question identifiers;
- QoI name and scientific definition;
- operator from a closed V0.3 set;
- an ordered list of `OperandSelector`s, each binding a name, variable, `value_role`, unit, scope,
  and locator policy;
- output unit;
- ordered expected membership;
- explicit trend tolerance in the output unit;
- missing-data policy;
- comparison and V&V report fingerprints;
- observation input fingerprint;
- candidate status.

V0.3 operators are deliberately narrow:

- `identity`: consume one `precomputed-qoi` or one already exported scalar per expected member;
- `difference`: subtract two explicitly identified exported scalar roles per member;
- `ratio`: divide two explicitly identified exported scalar roles per member, with zero-denominator
  rejection;
- `relative-change`: compare each scalar member with an explicitly declared reference member.

No expression language or model-generated formula is introduced.

The operator grammar is exact. `identity(A)=A` requires one operand. `difference(A,B)=A-B` requires
two dimensionally compatible operands converted to the declared output unit. `ratio(A,B)=A/B`
requires two dimensionally compatible operands, produces unit `1`, and rejects `B=0`.
`relative-change(A; reference)=(A-A_ref)/A_ref` uses one operand plus an explicit reference member,
produces unit `1` (or `%` by declared formatting conversion), and rejects `A_ref=0`. Operand count,
ordering, and unit rules are validated before locking.

### 8.2 Checkpoint 1 and lock

The author locks one candidate with:

- candidate ID;
- author identity;
- exact candidate fingerprint;
- timestamp.

The locked object contains the same scientific content plus approval metadata. A candidate fingerprint
mismatch, topic change, observation change, or comparison/V&V change prevents locking.

Direction-only topic approval cannot be used to lock a manuscript QoI contract.

### 8.3 Analysis

Analysis:

1. reloads and fingerprints the canonical observations;
2. verifies that every locked input fingerprint still matches;
3. orders rows by expected membership;
4. converts compatible units to contract units;
5. executes the closed operator;
6. verifies finite outputs and missing policy;
7. classifies the complete discrete sequence;
8. emits locked QoI values, overall change, trend result, restrictions, and backlinks.

`DiscreteTrend` is a closed V0.3 result set: `monotonic-increasing`, `monotonic-decreasing`,
`interior-peak`, `plateau`, and `overall-change`. Trend classification requires at least three distinct coordinate values and an explicit finite,
nonnegative tolerance. With two points, the system may report only an endpoint/overall change. With
fewer than two points, it reports insufficient evidence. Nonuniform coordinates remain nonuniform;
the system does not interpolate them.

For three or more points, the existing `detect_trend` result maps directly for monotonic increase,
monotonic decrease, interior peak, and plateau; `interior-trough` and `mixed` map to
`overall-change`. Two points always map to `overall-change`. `overall-change` retains endpoint delta
and direction metadata but is not relabelled as monotonic. No monotonic/peak/plateau label is emitted
without both three points and the explicit tolerance.

## 9. Claim ceiling and candidate figure contract

### 9.1 Four closed levels

V0.3 uses only:

1. `no-numerical-claim`;
2. `directional-comparison`;
3. `qualified-numerical-observation`;
4. `supported-physical-interpretation`.

The ceiling is computed deterministically from qualification, V&V, QoI completeness, trend support,
and unresolved differences. Plotting, writing, QA, author phrasing, or model output cannot raise it.

The exact upper bounds are:

- insufficient comparison or missing executable QoI → `no-numerical-claim`;
- incomplete quantitative bindings → at most `directional-comparison`;
- `restricted` may reach `qualified-numerical-observation` only when its contract explicitly permits
  quantitative reporting and every reported QoI has a complete unit and locator;
- `eligible` with complete located QoIs → at most `qualified-numerical-observation`;
- `supported-physical-interpretation` requires `eligible`, relevant verification and validation
  demonstrated for the intended use, complete locators, and no unresolved nuisance relevant to the
  interpretation.

No level is inferred from a status string alone, author approval, visual QA, or prose quality.

### 9.2 CandidateFigureContract

`analyze` creates a `CandidateFigureContract` containing:

- candidate figure ID and analysis fingerprint;
- primary bounded claim text and ceiling;
- evidence IDs and numeric backlink IDs;
- one panel specification;
- x/y variable, units, expected cases, and ordering;
- allowed visual encoding;
- prohibited inferences;
- paragraph duty and caption duty;
- candidate status.

The V0.3 panel is a discrete marker-and-line comparison. Lines connect observed discrete members for
readability; the contract and caption forbid interpretation as an interpolated response surface,
continuous optimum, stability boundary, or unsampled prediction.

### 9.3 Checkpoint 2 and conversion

Checkpoint 2 binds:

- qualification report;
- V&V status;
- locked QoI analysis;
- computed ceiling and claim;
- CandidateFigureContract;
- paragraph duty;
- author identity and exact fingerprint.

After approval, the candidate converts to the existing `contracts.FigureContract`. Conversion does
not mutate the existing public model. It populates:

- `figure_id` from the candidate;
- `primary_claim_id` from the bounded claim;
- `evidence_ids` from locked analysis;
- `panels` with the single approved panel ID;
- `source_data_uri` with the deterministic output CSV path;
- `prohibited_inferences` from the candidate.

No figure is rendered before conversion succeeds.

## 10. Figure production

### 10.1 Deterministic delivery

For one locked FigureContract, `figure` writes:

```text
.cfdpaper/outputs/figure/<figure_id>/
├── source-data.csv
├── plot_<figure_id>.py
├── <figure_id>.svg
├── <figure_id>.png
├── caption.txt
├── qa-data.json
├── qa-narrative.json
├── qa-visual.json
└── delivery.json
```

The script is runnable from a clean project environment and reads `source-data.csv` relative to its
own directory. It contains no project-specific absolute path.

The source-data CSV contains only approved, plotted fields and backlinks:

- case ID;
- coordinate value and unit;
- QoI value and unit;
- trend/role fields needed for display;
- evidence ID and source locator.

### 10.2 Matplotlib contract

The renderer uses Matplotlib and a restrained journal-oriented default:

- readable serif-compatible font fallback;
- explicit axis labels and units;
- discrete markers whose visual encoding does not rely on color alone;
- light major grid only;
- no smoothing, fit, uncertainty band, or continuous color field;
- SVG editable text and PNG preview;
- deterministic dimensions and DPI;
- no PDF or TIFF output in V0.3.

Matplotlib is the only new runtime dependency required by the vertical slice.

### 10.3 Three QA dimensions

Data QA recomputes and checks:

- source-data row count and order;
- case membership;
- values and compatible units against locked QoI results;
- evidence IDs and locators;
- source-data and artifact bindings.

Narrative QA checks:

- claim and caption do not exceed the ceiling;
- trend wording matches the locked trend;
- prohibited inference phrases are absent;
- every stated number has a backlink.

Visual QA checks deterministic properties that software can verify:

- SVG and PNG are nonempty and structurally valid;
- axis labels and units are present;
- expected cases appear in SVG text;
- the generated script declares distinct marker/line semantics;
- no artist is clipped according to a post-draw bounding-box check;
- image dimensions meet the fixture contract.

V0.3 does not claim that automated checks replace an author's aesthetic review. The result remains a
candidate until checkpoint 3.

## 11. Evidence-bound results paragraph

### 11.1 Restricted renderer

`write --artifact results-paragraph` uses a deterministic renderer. It consumes only checkpoint-2
approved objects and produces exactly one paragraph plus a structured backlink map.

The paragraph has four duties:

1. identify the compared cases and prescribed coordinate;
2. report the primary discrete trend or overall change;
3. give the approved quantitative evidence with units;
4. state the interpretation allowed by the ceiling and one necessary boundary when material.

It does not include methods prose, literature review, a general conclusion, or process/audit language.

### 11.2 Numeric backlinks

Every formatted number is represented first by a `NumericBacklink` containing:

- backlink ID;
- case/member ID;
- value before formatting;
- unit;
- QoI result ID;
- evidence ID;
- source locator;
- formatting rule.

The renderer first inserts a unique opaque placeholder for each backlink, for example
`{{NB:nb-0004}}`, then replaces placeholders exactly once with formatted values. It verifies token
set equality before and after assembly. It never scans arbitrary digit characters: case IDs, figure
IDs, citation labels, and section numbers are not scientific numeric claims. Missing, duplicated, or
unused backlink tokens block delivery.

### 11.3 Optional model polish

Host-model polish is outside the authoritative V0.3 path. A host may offer a candidate rephrasing,
but it cannot replace the deterministic paragraph unless a later version provides an explicit fact
equivalence validator. Provider transport is not implemented or tested in V0.3.

## 12. Stale propagation

The workflow has one `ScientificInputFingerprint` over:

- observation bytes;
- expected membership;
- locked QoI contract;
- comparison qualification;
- verification/validation status;
- `UNIT_REGISTRY_VERSION` and a canonical digest of the unit definitions used;
- approved topic fingerprint.

The analysis, candidate/locked figure contract, figure delivery, and paragraph each record the
upstream fingerprint they consumed.

Before `analyze`, `figure`, or `write` reuses an artifact, it recomputes the fingerprint. A mismatch:

1. marks the dependent artifact stale in its JSON status;
2. prevents consumption;
3. prints the first changed dependency category;
4. directs the user to rerun the earliest affected command.

The input source itself is never rewritten. An unchanged fingerprint permits deterministic resume.

## 13. CLI and checkpoints

### 13.1 Commands

`inspect` retains V0.2 behavior.

`qualify`:

```text
cfdpaper qualify PROJECT_ROOT --records project-records.json --observations observations.csv --question "..."
cfdpaper qualify PROJECT_ROOT --observations observations.csv --guided --question "..."
cfdpaper qualify PROJECT_ROOT --observations observations.csv \
  --records project-records.json \
  --approve-qoi-contract qoi-pressure-drop --author "Author Name"
```

The first two forms write qualification and candidate QoI artifacts through the same strict intake;
the guided form additionally creates `project-records.json`. The approval form reruns validation,
requires an exact candidate fingerprint, and records checkpoint 1.

`analyze`:

```text
cfdpaper analyze PROJECT_ROOT
```

It requires checkpoint 1 and writes locked analysis, ceiling, bounded claim, candidate FigureContract,
and paragraph duty.

`figure`:

```text
cfdpaper figure PROJECT_ROOT \
  --approve-contract fig-pressure-drop --author "Author Name"
```

It verifies the candidate fingerprint, records checkpoint 2, converts to `FigureContract`, renders
the figure, and writes QA.

`write`:

```text
cfdpaper write PROJECT_ROOT --artifact results-paragraph
cfdpaper write PROJECT_ROOT --artifact results-paragraph \
  --approve-final --author "Author Name"
```

The first form writes the deterministic paragraph. The second revalidates the current figure and
paragraph and records checkpoint 3 without changing their content.

Approval options are paired; author identity alone never approves an object. Existing `review`,
`revise`, and `export` roadmap commands remain unavailable.

### 13.2 Three checkpoints

1. `qoi-contract-approved`: approved topic/question and exact CandidateQoIContract;
2. `figure-claim-approved`: qualification, V&V, QoI analysis, ceiling, claim,
   CandidateFigureContract, and paragraph duty;
3. `v03-artifact-approved`: final figure, caption, QA, paragraph, and backlinks.

The checkpoint count remains three. Figure QA does not create a fourth approval stage.

## 14. Four thin Skills

V0.3 ships four Skills:

1. `cfd-evidence-intake` wraps `inspect` and `qualify` and explains minimum correction requests;
2. `cfd-qoi-physics` wraps checkpoint-1 locking and `analyze`;
3. `cfd-figure-production` wraps checkpoint-2 locking and `figure`;
4. `cfd-evidence-writing` wraps `write --artifact results-paragraph` and final approval.

Each Skill contains only `SKILL.md` and a small eval fixture reference. It does not duplicate Python
logic, store project state, define a second contract, or claim cross-host equivalence. Paths are
relative. Each declares trigger, do-not-trigger, inputs, outputs, prerequisites, workflow, stop
conditions, fallback, and success criteria.

## 15. Public fixture

V0.3 includes one public, non-sensitive, physics-grounded steady laminar pipe-flow fixture.

### 15.1 Positive case

The fixture contains three or more solver-export-like observations of inlet-to-outlet pressure drop
at prescribed mean velocities for fixed geometry and fluid properties. The oracle uses the
fully-developed laminar relation as an external check while preserving the exported values as the
plotted evidence.

The Hagen–Poiseuille relation is used only as an analytic numerical-verification reference. It is not
an external validation dataset for the modeled intended use. Therefore fixture validation is
`not-demonstrated`, and the maximum fixture ceiling is `qualified-numerical-observation`, never
`supported-physical-interpretation`.

The positive path demonstrates:

- complete case/coordinate membership;
- known compatible units and locators;
- intended velocity variation with fixed geometry/material/model;
- declared convergence and conservation evidence with basis/locator;
- `demonstrated` numerical verification and `not-demonstrated` validation as documented by the fixture;
- correct discrete trend and bounded ceiling;
- exact source-data, figure, caption, and paragraph backlinks.

### 15.2 Negative and adversarial variants

Variants cover:

- missing middle case;
- duplicate coordinate;
- unknown or incompatible unit;
- blank locator;
- `declared-aggregate` without aggregation;
- precomputed QoI presented as raw samples;
- unresolved geometry nuisance;
- unsupported `not-applicable` V&V status;
- request to infer an area integral from scalar rows;
- request to smooth into a continuous optimum;
- changed CSV after checkpoint 2.

Each variant has a machine-readable oracle stating the first blocking issue and the strongest allowed
ceiling. The fixture does not claim to validate all CFD software or physical domains.

V0.3 uses these deterministic paths:

```text

│   └── observations.csv                 # user-owned; never rewritten
└── outputs/
    ├── qualify/
    │   ├── qualification.json
    │   ├── candidate-qoi-contract.json
    │   └── locked-qoi-contract.json
    ├── analyze/

    │   ├── claim-ceiling.json
```

Atomic replacement is used for generated artifacts. The system does not create a parallel registry
for files already addressable through these deterministic paths.

## 17. Error and exit semantics

- malformed user input or missing approval: CLI exit code 2 with a concise correction;
- scientifically insufficient input: command completes with a structured `insufficient` report and
  no downstream artifact; CLI exit code 3;
- stale downstream artifact: CLI exit code 4 and the earliest rerun command;
- internal write/render failure: CLI exit code 1 without presenting partial output as complete;
- successful candidate or delivery: exit code 0 and artifact paths.

No traceback or prior report contents are printed by default.

## 18. Acceptance criteria

V0.3 is complete only when:

1. all seven work packages pass unit and end-to-end tests;
2. the public positive fixture reaches checkpoint 3 and reproduces the oracle;
3. every negative/adversarial variant stops at the expected boundary;
4. changing observations, expected membership, contract, or unit definition blocks old figure/text;
5. the figure includes source data, runnable script, SVG, PNG, caption, and passing data/narrative/
   visual QA;
6. the paragraph contains no unbound number and does not exceed its ceiling;
7. the four Skills call the same CLI path and pass positive, negative, and adversarial evals;
8. `inspect` and `plan` retain their V0.2 behavior;
